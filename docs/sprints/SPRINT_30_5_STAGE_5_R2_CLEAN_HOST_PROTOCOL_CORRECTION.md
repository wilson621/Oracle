## Clean-host runtime

The permitted host surface is Windows PowerShell 5.1, Windows built-in APIs and
services, installed Microsoft Edge, and manifest-bound precompiled fixtures.
The provider binds only to `127.0.0.1`; qualification retains the no-default-
route gate and prohibits production endpoints and credentials.

The Edge semantic probe is implemented in Windows PowerShell using the browser's
DevTools protocol. It authenticates through the packaged `/auth` page and checks
all eight frozen protected routes for DOM and accessibility-tree semantics,
names, tab order, visible focus, contrast, 200-percent-equivalent reflow and
rendered reduced motion. The package observer and Companion controller retain
the accepted ownership verification and race-tolerant teardown policies.

## Lifecycle correction established

The preserved `installed-clean-host-03` failure was not repository-related. A
Windows Restart Manager inspection identified the exact owner of the locked
`Default\Cache\No_Vary_Search\journal.baj`: the re-parented Microsoft Edge
`network.mojom.NetworkService` process for the probe's exact generated profile.
The former teardown stopped only the launcher and raced recursive profile
removal while that owned child still held the cache journal.

The corrected probe sends `Browser.close`, waits for bounded natural exit,
re-discovers only `msedge.exe` processes whose command lines bind the exact
profile, verifies their admitted executable and creation identity, stops only
verified survivors, proves zero profile processes, and only then removes the
profile with a bounded retry. Fresh success and failure-path source integrations
both recorded zero remaining profile processes and successful profile removal.

The caught-exception diagnostic also established that the clean-host provider's
CORS preflight omitted the real client's `X-Supabase-Api-Version` header. The
allow-list and an exact browser-preflight regression were corrected. A separate
source-harness omission of the already-required non-production web-session
integrity secret was corrected without changing the installed lifecycle.

## Qualification impact and blocker

The lifecycle and clean-host fixture corrections change no product source,
accepted package, production provider or accepted evidence. On their own they
do not trigger Stage 2, Stage 3 or Stage 4 requalification.

defect before another installed rehearsal: enabled informational text using the
R6 `text-slate-500` style renders at approximately 4.22–4.25:1 on its actual
backgrounds, below the frozen 4.5:1 Stage 5 threshold. The exact style is present
in candidate tree `ee8fbeb7a8d18d393cc9a3e92d622250eb2165ff`; it is not a
source-worktree regression. Disabled controls were excluded under the WCAG
inactive-control exception, and source-only Next development portal focus nodes
were separated from installed focus claims.

Stage 5 preparation cannot truthfully close against the unchanged R6 MSIX.
Correcting the product would create a new MSIX baseline and invalidate the exact
package binding of accepted R6/R12/R4 for future-chain purposes, requiring a new
governed requalification chain beginning at Stage 2. No product change has been
made. The Founder must either authorise that product correction and resulting
requalification mission, or accept that Stage 5 cannot qualify the unchanged R6
baseline. Weakening the frozen threshold is not recommended.

Both R1 transfers remain immutable pre-authority engineering failures and are
prohibited from admission or execution. No R2 transfer, authority or attempt
